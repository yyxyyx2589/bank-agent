# 瓶颈不是模型大小，是知识边界

> 一次「银行远程银行坐席知识助手」的完整复盘：21 道题、3 条基线、1 次消融，以及我在这中间踩掉的 6 个坑。
>
> 发布渠道：掘金 / 知乎（技术长文体）。仓库：[github.com/yyxyyx2589/bank-agent](https://github.com/yyxyyx2589/bank-agent)

## 一、背景：我为什么做一个"客服助手"这种听起来很无聊的东西

先说动机，因为动机决定了后面的取舍。

银行放贷、拉存款、卖理财，最后都要落到"人接电话"这一环。坐席接起来，客户问"我这张卡丢了怎么办""12 期手续费多少""我能不能帮我妈代办开卡"。坐席要在几秒内答出**准确的业务规则**——答错是事故，编造是违规。

这个场景有个很硬的性质：**它同时要求"答得快"和"不许错"**。而大模型天然是"永远敢答"的。所以这个场景里，模型能力不是主要矛盾，**"它什么时候不该答"才是**。

我原本有一个运维场景的项目（`ops-agent`，企业 IT 运维智能体）。它的核心设计恰好就是这件事：

> 把 RAG 的检索置信度（相似度 `sim` / 关键词覆盖率 `kw_coverage`）从「相关度分数」升级成「**决策路由信号**」。

在运维场景里，这是个工程优化；在银行场景里，这一下子变成了**合规刚需**。所以我没有重新发明轮子，而是做了一次**同构换皮**：编排骨架（三级路由 + ReAct 工具循环 + 双引擎）完全复用，换掉的是知识库、工具集、业务数据和全部话术。

这不是偷懒。**"我有一套骨架，能低成本迁移到新行业"**这件事本身，比"我又从零写了一个 demo"更值钱。

## 三、做法：四个关键取舍

### 取舍 1：置信度阈值不是常数，是**跟语料绑定的标定量**

原项目那套阈值是 `0.70 / 0.45 / 0.30`，针对 **15 条英文技术 KB** 标的。

换到 **24 条中文银行业务 KB** 之后，我直接沿用旧值，结果**标准业务问题被大面积误判为低置信**、误入转人工。原因很直白：中文银行语料里"开卡 / 补卡 / 挂失 / 销户"彼此语义高度接近，**整个相似度分布往下移了**。

按实测重标为 `0.55 / 0.40 / 0.15`（正样本 `sim ∈ [0.445, 0.880]`，负样本 `sim ≤ 0.434`）。

**教训**：相似度阈值是**检索器和语料共同决定**的，换个知识库它就是另一个数。看到"沿用原阈值"这种操作，基本可以判定对方没有做过标定。

### 取舍 2：高置信 ≠ 应当直答——两类问题必须"绕过知识库"

这是我做完之后回头看，最值得讲的一个点。

有两类问题，**知识库答得了，但答案不该由知识库给出**：

| 类型 | 例子 | 为什么不能直答 | 改写路径 |
|---|---|---|---|
| 具体数字 | 信用卡分 12 期手续费率是多少 | 制度文档只给区间"7%~9%"，精确值 **7.20%** 在产品参数表；且挂牌价会调整 | 进 `agent_loop` + `get_product_rate` |
| 条件判定 | 客户转 60 万需要提前预约吗 | 制度原文口径模糊"部分银行要求…"，逐条判定在业务规则表 | 进 `agent_loop` + `check_business_rule` |

所以路由里我加了两个"覆盖谓词"：**即使 sim 高到可以直答，只要命中这两类，也强制改走工具调用**。

这就是"RAG"和"Agent"最本质的差别：**RAG 回答"文档里写了什么"，Agent 回答"这件事该怎么办"。** 前者是检索问题，后者是决策问题。

我把这类问题专门做成了评估集里的题——因为**它们才是通用 RAG 真正答不了的地方**，也正是我这套编排的价值所在。

### 取舍 3：新增一个"主动转人工"的工具

原项目里"转人工"是**路由层的兜底文案**（被动：答不出来才转）。银行场景里，"该不该自己处理"本身是个**需要 Agent 主动判断的合规决策**。

所以我把它做成了一个工具 `escalate_to_human`，参数是 `priority`（紧急/一般）和 `suggested_team`。

**而这个工具差点成为摆设——这是本次最值得说的一个坑。** 见下一节。

### 取舍 4：双编排引擎，并用固定剧本证明两者等价

同一套逻辑，我用手写 ReAct 主循环和 LangGraph 各实现了一遍（`agent.py` / `agent_langgraph.py`），然后用 **11 个固定场景**断言两者**逐项等价**。

理由：一是验证"框架不引入行为漂移"，二是——**面试里被问"为什么不用 LangChain"时，我能拿测试说话，而不是拿观点说话**。

## 四、六个坑（这才是这篇文的价值所在）

### 坑 1：功能写完了 ≠ 功能可达——`escalate_to_human` 的死代码

收口审查时我逐条走查，发现一个尴尬的事实：**`escalate_to_human` 从来没有被调用过。**

原因是链路顺序错了：

1. 客户说"我要投诉"；
2. 这句话在制度文档里**不存在**，检索 `sim` 只有 0.13~0.33；
3. 于是必然落进**低置信兜底**，被 `refuse_human` 用"超出知识库范围"打发掉；
4. **Agent 根本没机会看到这类问题。**

也就是说，我精心设计的那个工具，被上游的路由层**先一步截胡**了。

修复分三步，每一步都是被上一步的实测逼出来的：

1. **把升级判定提到阈值决策之前**（顺序错了，后面的逻辑再完美也没用）；
2. **按语境区分**"客户要投诉"和"坐席查投诉记录"——后者是正常检索，不该触发转人工；
3. **两档（资金安全 / 投诉要求人工）都用 `tool_choice` 强制首轮调用**——因为实测**只靠提示词的服从率只有约 50%**。

**教训**：写完一个功能，要问的不是"代码对不对"，而是"**这条路径真的会被走到吗**"。**最危险的不是报错，是静默地永不执行。**

### 坑 2：评估集标注太松 = 给自己发假成绩

我有两道题的期望要点标得太宽：

| 题 | 原标注 | 纯 RAG 实际答的 | 结果 |
|---|---|---|---|
| B20 | `["转接"]` | "无法判断…请转接人工" | 命中了子串，**判满分** |
| B16 | `["投诉"]` | "**无法判断**该客户有无投诉记录…向人民银行分支机构投诉" | 出现"投诉"二字，**判满分** |

纯 RAG 明明**答的是"我无法判断"**，却因为句子里蹦出了关键词就被判对。收紧成 `["投诉处理组"]` / `["没有投诉记录"]` 之后，两条 RAG 基线**各掉 1 题**。

**教训**：评估集的**松紧本身就是被测对象**。标注一松，分数就是自欺——而且它和"泄漏"一样，**失真从数字上看是好消息**，所以特别容易被将就过去。

### 坑 3：中间基线是假的（以及我自己给自己挖的三个坑）

评估表里得有一条"私有化小模型"的基线——因为银行有个绕不开的约束：**客户数据不能出内网**。那就得私有化部署。

"小模型 + 域微调，效果会掉多少？"——这个数字不给出来，"Agent 编排值多少"就只是一句口号。

所以我自己训了一个：基座 `Qwen2.5-1.5B-Instruct` + 自建银行域 LoRA，**RTX 4060 Laptop 上 5.4 分钟**（303 条样本，loss 0.47 → 0.018）。

但这条基线最大的风险不是训不出来，而是**我会不自觉地给它作弊**。我提前挡掉了三个诱惑：

| 诱惑 | 做法 | 为什么危险 |
|---|---|---|
| 把精确数字训进去 | **只训知识库语料**，不训 products / business_rules 表里的数字 | 那些数字正是"检索拿不到、只有 Agent 调工具才有"的。训进去 = 中间基线靠背答案虚高，三基线对比立刻失效 |
| 训练数据用"裸问题 → 答案" | **RAG 范式对齐**：messages 与推理时**逐字同构**（system + 检索片段 + 问题 → 答案），并做 completion-only loss mask | 只喂裸问答，模型学成**直答器**；推理时塞给它检索片段，它反而当噪音忽略 |
| 训练问法只做"完全相同"剔除 | **两道闸门**：完全相同剔除 + 字符相似度 ≥0.72 剔除 | 第一版只做精确匹配，**剔除了 0 条**，看着很干净；但实际有 **8 条近重复**（训练问"银行卡丢了要怎么补办呢" / 评测题"银行卡丢了怎么补办"）。近重复同样构成泄漏 |

第三点补充一个细节：训练集与评测题**最接近的一对相似度是 0.690**，刚好卡在 0.72 阈值下方。而它对应的那道题（B13），中间基线**恰好答错了**——因为要的精确值 7.2% 只存在于产品表、不在知识库里。

**这说明"问法相近"不等于"能拿到答案"**：能不能答取决于**知识边界**，不取决于问法。所以那 0.690 的一对我**保留了**，没有为了让指标好看去压阈值。

### 坑 4："我训了 LoRA"和"LoRA 带来了多少"是两件事

上面那些只说明我**做了**微调，没说明微调**有什么用**。

所以我补了一个**消融**：同一条检索链路、同一份提示词，**唯一差别是不挂 adapter**。

| | 端到端解决率 | 答案中位长度 | 平均延迟 |
|---|---|---|---|
| 纯基座（不挂 adapter） | 59.5% | 76 字 | 1862 ms |
| **+ 银行域 LoRA** | **66.7%** | 144 字 | 6152 ms |

**LoRA 修好了 3 道题、弄差了 0 道。** 原因看一眼答案就明白了——基座答得太短：

- 「房贷提前还款」：基座只答违约金比例（1%~3%），**漏了"需提前 15~30 个工作日预约"**；
- 「理财产品 R3」：基座只答"可能有本金损失"，**漏了"中风险"这个等级定位**。

也就是说，LoRA 学到的**不是新知识**（知识本来就在检索片段里），而是**把"按坐席口径完整作答"这个行为压了进去**：不截断、不漏要点、覆盖例外情形。

**这正是 SFT 在 RAG 链路里该干的事。** 而且"59.5% → 66.7%"这个数字，比"我训了个 LoRA"有力得多。

> 诚实边界：延迟从 1862ms 涨到 6152ms，方向与答案变长一致（长度 ×1.9、延迟 ×3.3）。涨幅不完全成比例，剩余部分的归因我**没有进一步验证，如实留在表里不猜**。

### 坑 5：前端多轮渲染的 bug，HTTP 层测试永远抓不到

Web 端有个 bug 从第二轮起，路由徽章 / 工具时间线 / 答案**全部渲染进了第一轮的气泡里**。

根因：每一轮都用同一套 `id` 当锚点（`cur-bubble` 等），而 `getElementById` **只返回第一个匹配**。

而我的 `verify.py` 校验的是"同一 session 两轮后历史 4 条"——**HTTP 层完全覆盖不到这个 bug**。

只有一件事抓到了它：**我把界面真截图出来看**。修法是新一轮开始前先把上一轮的锚点 id 摘掉。

**教训**：单元测试测的是"你以为会发生的事"。**廉价的验收测试（截图）能抓到单元测试结构上抓不到的东西**——这也是我坚持给 README 配实跑截图的原因，配图顺手又抓到两个真 bug。

### 坑 6：延迟数字里混进了"冷启动"

第一版延迟统计里，**第 1 题有 36 秒**。这不是模型慢，是 TLS 握手 + embedding 模型懒加载 + 本地模型 CUDA kernel 预热全记在了第 1 题头上。

修法是**预热**：正式统计前先跑一次不计入的空调用。修正之后平均延迟从虚高的数字回到正常的 2425ms。

**教训**：性能数字的**口径**比数字本身重要。不写清口径的延迟数据，等于没有。

## 五、数据：三条基线，21 道题

评估集 21 道题，覆盖三条路由、四类工具、以及"知识库答不了"的边界问题。

| 指标 | 纯 RAG（云端大模型） | RAG + LoRA（本地 1.5B） | **Agent（本项目）** |
|---|---|---|---|
| 端到端解决率 | 69.8% | 66.7% | **100%** |
| 路由准确率 | 33.3% | 33.3% | **100%** |
| 平均延迟 | 1223 ms | 6152 ms | 2425 ms |

**最关键的一个观察：两条 RAG 基线失败的题完全重合**——同样 7 道（B09/B10/B12/B13/B16/B20/B21），无一例外都是"**答案不在知识库里**"的（工单状态、精确年利率、精确分期费率、有没有投诉记录、要不要转人工）。

于是结论就非常清楚了：

> 把作答模型**从小换到大**（1.5B → 云端大模型），分数只动了 3 个点（且在波动范围内）；
> 把"**没有编排**"换成"**有编排**"，从 ~68% 到 100%。

**这个场景下模型大小不是瓶颈，知识边界才是。补上边界的不是更大的模型，是编排层。**

顺带一个工程细节：本地模型我用**贪心解码**。一方面小模型采样容易跑偏、复读；另一方面是让"稳定性"这个指标变干净——如果解码带随机性，极差里就混进了采样噪声，说不清波动来自模型能力还是随机种子。贪心之后中间基线的极差是 **0**。

## 六、不足：哪里还没做好

写技术文最容易犯的毛病是把"不足"写成"下一步规划"。我这三条是真的没做好：

1. **21 道题太少，且是我自己出的。** 它验证的是"设计意图被正确实现"，**不是生产准确率**。真要上线，得有几百条真实坐席日志抽样的评测集。这个规模下 100% 这个数字，我不想过度解读。
2. **本地小模型慢 5 倍**（6152ms vs 1223ms）。私有化换来的是"数据不出内网"，**不是速度**。真实坐席场景里这个延迟大概率不能接受，需要量化/蒸馏/更小的模型。
3. **`escalate_to_human` 是演示桩**，只生成转接单号，没有真实工单流转；也没有做权限与审计留痕。**"可问责"这一环我只做到了一半。**
