# 产品设计书 · 银行远程坐席知识助手（多 Agent v2）

> 版本：v2.0 ｜ 日期：2026-10-20 ｜ 前置：v1 单 Agent 版（`D:\job-portfolio\bank-agent`）
> 本文回答三个问题：**为什么升级多 Agent、拆成哪几个 Agent、做到什么程度算合格。**

---

## 1. 业务背景与痛点

远程银行中心坐席在通话中面对三类硬约束：

| 约束 | 含义 | 违反后果 |
|---|---|---|
| **不能错** | 费率、限额、流程必须给精确值 | 客户损失 → 投诉/事故 |
| **不能编** | 超出知识边界必须拒答或转人工 | 监管违规 |
| **要快** | 坐席只有几秒钟组织答案 | 通话时延拉长，体验下降 |

v1 用「单 Agent ReAct 循环 + 三级置信度路由」解决了基础问题，但暴露了三个架构性短板：

1. **职责耦合**：合规判断（该不该答）和业务回答（怎么答）在同一个循环里，靠提示词约束，实测资金安全场景提示词服从率仅约 50%——v1 是靠路由层强制工具调用兜底的，说明"合规不该是模型的心情"。
2. **上下文膨胀**：5 个工具描述 + 全部业务话术塞进一个上下文窗口，工具再增加时路由质量退化（业界共识：单 Agent 超过 5~7 个职责即到顶）。
3. **评测口径脏**：一次失败分不清是检索错、判断错还是生成错，评测没法归因。

## 2. 为什么是多 Agent（而不是"为多而多"）

调研 2026 年生产实践与开源对标（LangGraph 官方 supervisor 模式、SurajBilgi/Multi-Agent-Generative-AI-Banking-Assistant、cockroachlabs/banko-ai-assistant 等）后确定的拆分原则：**只有当某一职责需要独立的成功标准、独立的最小工具权限、或独立的失败隔离时，才值得拆成独立 Agent。**

据此拆分，每个 Agent 都能回答"为什么不并进邻居里"：

| Agent | 职责 | 为什么独立 |
|---|---|---|
| **Guard 合规守卫** | 行外护栏 / 投诉 / 资金安全 / 要求人工的前置识别 | 合规判断必须**先于且独立于**业务生成；规则引擎优先，不依赖 LLM 心情；漏判是监管事故，需要 100% 命中率的独立评测 |
| **Supervisor 编排** | 显式规则路由，决定下一个 Agent | 唯一持有全局视图的角色；用确定性规则优先（置信度、gate 结果），LLM 只做兜底判断——区别于开源项目纯 LLM 路由 |
| **Knowledge 知识检索** | RAG 证据包 + 置信度评估（sim / kw_coverage） | 检索质量有独立成功标准（命中率/置信度校准），工具只有 rag_search，权限最小化 |
| **Rules 业务规则** | 费率表 / 业务规则表的**逐条判定** | 处理「制度文档只给区间、精确值在结构化表」的硬场景；和 RAG 是完全不同的失败模式 |
| **Ticket 工单处置** | create_ticket / escalate_to_human | 全系统**唯一有副作用的 Agent**（建工单、转接人工），权限隔离 = 出事时爆炸半径最小 |
| **Synthesis 答案合成** | 组装带引用的可溯源答案 | 答案口径统一（引用 kb-xxx / R-xxx / 工单号），是合规问责的落点 |

> Guard 与 Supervisor 的关系：Guard 是**必经的第一道闸门**（不在 Supervisor 的调度环内），输出 `gate` 决定（PASS / REFUSE / ESCALATE）；Supervisor 只在 PASS 之后开始调度。这样"该不该答"和"怎么答"在图结构上就分开了。

## 3. 用户与场景

**用户**：远程银行中心坐席（含网点柜员）。助手不是面向客户的，是**给坐席看的第二屏**。

| # | 用户故事 | 走哪条 Agent 链路 | 验收要点 |
|---|---|---|---|
| U1 | 客户问「信用卡分 12 期手续费多少」 | Guard→Supervisor→Rules→Synthesis | 给精确值 7.20%（产品参数表），而不是制度文档的「7%~9%」 |
| U2 | 客户说「我卡被盗刷了」 | Guard（资金安全）→Ticket | 不追问身份、不查知识库；直接升级反欺诈组并给自助动作 |
| U3 | 客户问「你们能推荐哪只基金吗」 | Guard（行外护栏）→REFUSE | 标准拒答话术，不进任何业务 Agent |
| U4 | 坐席查「大额转账怎么预约」 | Guard→Supervisor→Knowledge→Synthesis | 高置信直答，答案带 kb 编号引用 |
| U5 | 客户问「转 60 万要预约吗」 | Guard→Supervisor→Knowledge→Rules→Synthesis | 知识库给不出精确判定，必须落到规则表逐条判定 |
| U6 | 客户投诉服务态度 | Guard（投诉）→Ticket | 转投诉专席，AI 不解释不辩解 |
| U7 | 知识库外的问题（sim 低） | Guard→Supervisor→（一轮补检索后仍不足）→拒答或转人工 | 不编造；低置信有明确出路 |

## 4. 功能范围

**In scope（本期交付）**
- 多 Agent 图：Guard → Supervisor{Knowledge, Rules, Ticket, Synthesis}，LangGraph 实现
- 置信度评估：复用 v1 口径（sim / kw_coverage 三档：direct ≥0.55 / loop ≥0.40 / refuse <0.40）
- 工具集：rag_search、get_product_rate、check_business_rule、create_ticket、escalate_to_human
- FastAPI 服务（POST /chat）+ CLI 双入口
- 评测：v1 评测集 21 题复跑 + 多 Agent 新增指标（路由归因）
- 测试：mock 单测（图结构/守卫/路由）+ 真实 LLM 冒烟

**Out of scope（明确不做）**
- 不面向客户直接服务（无客户端话术管理）
- 不做真实银行系统对接（工单落 SQLite 模拟）
- 不做前端界面（v1 已有 web，v2 先收 API/CLI 口）
- 不做 LoRA 训练线（v1 已沉淀 bank_sft.jsonl，本期专注编排架构）

## 5. 验收标准（可量化）

| 指标 | 目标 | 度量方式 |
|---|---|---|
| 评测集路由正确率 | ≥ 90% | evals/run_eval.py，21 题复跑 |
| 行外护栏命中率 | 100% | 荐股/收益承诺类不许漏过一个 |
| 资金安全转接率 | 100% | 盗刷/非本人交易必须转人工 |
| 答案可溯源率 | 100% | 直答必有引用；拒答必有标准话术 |
| Supervisor 循环上限 | ≤ 3 轮 | 图内硬编码，超限强制收敛 |
| 副作用隔离 | Ticket 是唯一写操作 | 代码审查 + 单测断言 |
| 测试 | mock 全绿 + 真实冒烟通过 | pytest + smoke |
