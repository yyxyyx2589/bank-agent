# 场景设计：银行远程银行坐席知识助手

> 本作品是从 `ops-agent`（企业 IT 运维智能体）**换皮改造**而来的求职作品。
> 编排骨架（Router 三级路由 + ReAct 工具循环 + 双引擎）完全复用，替换的是**知识库、工具集、业务数据与全部话术**。

## 一、为什么选这个场景

### 1. 这是 2026 年银行 AI 落地量最大、最标准的形态

行业公开信息（2026 年）：

| 事实 | 来源 |
|---|---|
| 2026 上半年银行类机构智能体招标项目**占全行业近半数**，"搭建统一智能体开发平台"是绝大多数金融机构的核心诉求 | 中国新闻网上海站，2026-07-29 |
| 宇信科技中标某股份制银行**智能知识助手**项目：基于 LLM+RAG 构建"提问 → 精准文档召回 → 答案生成 → 原文溯源"全闭环，目标远程银行问答准确率 **90%+** | 央广网，2026-07-17 |
| 交通银行建立智能体平台提供"开箱即用"的大模型能力；企业级知识平台**"交行知道"**知识规模较年初翻番 | 武汉市委金融办转载，2026-09-08；央视网，2026-09-21 |
| 农行私有化部署 DeepSeek、Qwen；中信银行私有化部署 DeepSeek-V4、GLM5 | 央视网，2026-09-21 |
| 智能体已批量上岗：工行 600+ 场景、建行 600+ 场景、招行 1386 个、中信 1900+、邮储 370+ | 中国经济网，2026-09-03 |
| 行业仍处"场景验证 → 规模化复制"过渡期，**多数智能体集中于内部助手、客服辅助等低至中风险环节**；专家强调突破口是"可控、可用、可问责" | 中国经济网，2026-09-03 |

**关键结论**：银行落地最成熟的形态 = **内部知识问答 / 坐席辅助**，技术栈 = **LLM + RAG + 溯源**。
这正好是本项目的骨架，改造是"同构替换"而非"重新发明"。

### 2. 原项目的核心设计在银行场景里价值更大

原项目最核心的设计是：

> **把 RAG 检索置信度（sim / kw_coverage）从"相关度分数"升级为"决策路由信号"**

在运维场景里，这是一个工程优化；但在**银行场景里，这是合规刚需**——因为银行 AI 的硬约束是"不能幻觉、不能越权、必须可问责"。

| 路由分支 | 运维场景含义 | 银行场景含义（合规视角） |
|---|---|---|
| `rag_direct`（sim ≥ 0.55 且 kw_coverage ≥ 0.15） | 知识库高置信，直接答 | 标准业务问题，可直接答复客户 |
| `agent_loop`（0.40 ≤ sim < 0.55） | 信息不足，调工具补充 | 需要查工单/费率/规则才能答，进入受控工具调用 |
| `refuse_human`（sim < 0.40） | 拒答转人工 | **超出知识边界，必须转人工，禁止模型自由发挥** |

> **阈值必须随知识库重标**：原运维项目的 0.70 / 0.45 / 0.30 是针对 15 条英文技术 KB 标的；
> 换成 24 条中文银行业务 KB 后，相似度分布整体下移（"开卡/补卡/挂失"彼此语义高度接近）。
> 沿用旧值会把标准业务问题判为低置信、误入转人工。本项目按实测重标为
> **0.55 / 0.40 / 0.15**（正样本 sim ∈ [0.445, 0.880]，负样本 sim ≤ 0.434），
> 详见 `config.py` 顶部的标定注释。

此外，高置信并不等于"应当直答"。有两类问题知识库答得了、但**答案不该由知识库给出**，
路由会强制改走 Agent 查结构化表：

| 类型 | 例子 | 为什么不能直答 | 改写路径 |
|---|---|---|---|
| 具体数字 | 「信用卡分 12 期手续费率是多少」 | 制度文档只给区间「7%~9%」，精确值 **7.20%** 在产品参数表；且挂牌价会调整 | `agent_loop` + `get_product_rate` |
| 条件判定 | 「客户转 60 万需要提前预约吗」 | 制度原文口径模糊「部分银行要求…」，逐条判定在业务规则表 | `agent_loop` + `check_business_rule` |

三级路由天然对应了银行要求的"**风险分级处置**"，这是这个作品最强的叙事点。

## 二、工具集设计（5 个）

原项目 5 个工具 → 银行版 5 个工具，一对一替换 + 新增 1 个合规兜底工具。

| 银行版工具 | 作用 | 入参 | 对应原工具 |
|---|---|---|---|
| `search_knowledge` | 检索行内制度/产品/业务规则知识库，返回片段 + 相似度 + 关键词覆盖率 | `query`, `top_k` | `rag_search`（保留，改描述与库名） |
| `query_ticket` | 查客户的业务工单/来电记录（"他上次来问什么"） | `customer_id`, `category`, `hours` | `query_log` |
| `get_product_rate` | 查产品利率/费率/期限/起存金额 | `product_category`, `term` | `get_monitor_metrics` |
| `check_business_rule` | 业务规则校验（能否代办、需不需要预约、额度上限） | `scenario`, `params` | `run_diagnostic_command` |
| `escalate_to_human` | **主动转人工**：识别出超权限/高风险/需双人复核的情形 | `reason`, `priority` | 新增（原项目由路由层兜底文案代替） |
| ~~`get_current_weather`~~ | 删除（原项目练手残留） | — | `get_current_weather` |

**设计说明**：新增 `escalate_to_human` 不是凑数。原项目里"转人工"是**路由层的兜底文案**（被动）；
银行场景里"该不该自己处理"本身就是一个**需要 Agent 主动判断的合规决策**（主动）。
把这个判断交给 Agent 工具，恰好体现了"从 RAG 到 Agent"的演进价值。

## 四、业务数据表

替换原 `logs / metrics / sessions`，改用：

```
tickets          -- 业务工单：客户历史来电与处理记录
  id, timestamp, customer_id, category, channel, status, summary, handler

products         -- 产品费率：存款/贷款/信用卡/理财的利率与规则
  product_code, name, category, rate, term, min_amount, effective_date, note

business_rules   -- 业务规则：可办理条件、限额、所需材料
  rule_code, scenario, condition, requirement, limit_amount, note

sessions         -- 会话记录（保留，结构不变）
```

## 六、诚实边界（写进 README，面试时必须说清）

- **数据是模拟的**：工单、交易、费率数据由脚本生成，不涉及任何真实机构与客户信息。产品费率参照公开信息设定，仅用于演示。
- **不是生产系统**：没有接入真实核心系统、没有做权限与审计留痕，`escalate_to_human` 是演示桩而非真实转接。
- **价值在编排设计**：本作品证明的是"如何用置信度路由把 RAG 的幻觉风险变成可控的分级处置流程"，而不是"我能做银行核心系统"。
