## 3. 多 Agent 架构验证

六个节点全部按设计运行，trace 字段可归因每一次决策：

| 节点 | 验证场景 | trace 证据 |
|---|---|---|
| Guard | 荐股拒答 / 盗刷转接 / 投诉查询语境排除 / 问候 | guard:REFUSE / guard:ESCALATE_FUND / guard:PASS / guard:GREETING |
| Supervisor | 高置信直答 / 中置信补查 / 低置信兜底 / 循环收敛 | 路由全部确定性，无 LLM 参与 |
| Knowledge | RAG sim=0.764 命中 kb-008 | knowledge:search sim/kw/level |
| Rules | 分期手续费查 XY003=7.20% / 大额转账触发判定 | rules:tool_calls |
| Ticket | 盗刷确定性转接 ZR 工单号 / 火锅兜底转人工 | ticket:escalate(deterministic) / ticket:llm_dispatch |
| Synthesis | 带引用答案 / 证据不足转人工 | synthesis:compose cites=N |

## 4. 关键设计决策验证

**为什么多 Agent 优于单 Agent（本项目实证）：**
1. **合规独立性**：Guard 纯规则引擎，资金安全/投诉 100% 命中，不依赖 LLM 心情（v1 提示词服从率仅 50%）
2. **评测可归因**：trace 字段让每次失败定位到具体节点（v1 单 Agent 分不清检索错/判断错/生成错）
3. **工具权限最小化**：Ticket 是唯一写操作节点，爆炸半径最小；Rules 拿不到 rag_search 避免重复检索
4. **确定性路由**：Supervisor 用置信度+关键词信号规则路由，不用 LLM 路由（开源项目普遍用 LLM 路由，不可解释）

## 5. 踩坑与修复记录

| 坑 | 现象 | 根因 | 修复 |
|---|---|---|---|
| ticket_intent 丢失 | 盗刷走了 LLM 分支而非确定性路径 | AgentState TypedDict 未声明 ticket_intent 字段，LangGraph 丢弃 | state.py 补字段 |
| 荐股变体漏判 | "推荐哪只基金"没命中"推荐基金" | 中间隔词，纯字符串匹配失效 | 加组合匹配（推荐+基金/股票） |
| 投诉查询误判 | "查投诉记录"被当投诉转人工 | "投诉"关键词太宽 | 加查询语境排除（投诉记录/状态/历史） |
| 低置信死循环 | 火锅问题跑两轮 rules 仍合成 | supervisor 低置信分支没判 rules 是否跑过 | 加 rules_run 判断，跑过无证据→ticket |
| ticket 兜底 gate 未标 | 火锅走 ticket 但 gate 仍 PASS | ticket_node 兜底分支没改 gate | 补 gate=ESCALATE |
| 评测期望值过时 | v1 评测集按单 Agent 标的 | v2 设计口径升级（资金安全/投诉必转人工） | 重标 B18/B19/B20/B21 |
